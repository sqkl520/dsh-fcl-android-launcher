## M2 · 稳定性达标

**目标**：M1 跑通后，让核心链路在真机上**反复操作也稳**——不崩、不卡死、多实例不串台。
这一里程碑消化的是前几轮报告里"已识别但需真机确认/仍未做"的可靠性项。

> **现状（2026-10-30）**：第 1/2/3/5/6 条的**代码侧已全部落地**，第 4 条（厂商 ROM 保活）
> 本质是**真机验证项**（代码只能做到"声明齐全 + 被杀能恢复"）；但**完成判据的 4 个勾一个都没打过**
> —— 不是代码没写，而是"连续 20 次装/删/启/停""断网/转屏""双实例并发安装""锁屏后台 30 分钟"
> 这些**必须上真机反复操作**的判据从未系统性执行过。fix2~fix22 里的稳定性改动
> （如 fix11 的 seccomp 重试真正 fork、fix12 的"装好没"判据统一、fix19 的幽灵实例保护）
> 都是**真机上出了问题再修**的单点修复，不等于主动跑过 20 轮压力。

**要做的事**
1. ✅ **`PROOT_NO_SECCOMP` 自动兜底**（第五轮已实现）：就绪前退出且疑似 seccomp/ptrace 不兼容
   （退出码 >128 或日志含 seccomp/ptrace/bad system call 等）时，自动带该变量重试一次（每实例每次启动限一次）。
   真机上仍需确认"重试后确实能救活"。
2. ✅ **`Process.pid()` 兜底**（2026-10-06 已实现）：反射拿不到时，退回解析
   `/proc/self/task/*/children`（与"启动前拍下的子进程快照"求差集）。
   ★ 查 `api-versions.xml` 时发现这条兜底**不是可选项而是必需**：Android 运行时的
   `java.lang.Process` **根本没有 `pid()` 方法**（那是 Java 9+ 的 API，`android.jar` 里能编过
   只是编译期存根），所以真机上反射路径一次都不会成功。同时修掉了反射取值的装箱 bug。
   （第五轮已给 `kill()` 加 cmdline 身份校验，避免 pid 复用误杀。）
3. ✅ **`DshInstaller` 错误按 instanceId 分发**（第五轮已实现）：失败摘要/npm 错误尾巴改为按实例分表，
   消除双实例并发安装时的错误串台。**下载页进度标记串台（R5-17）也已在 fix13 补齐**：
   `reconcileInstalling(prev, event)` 只移除**本次失败/取消的那个版本**，不再清空整个集合
   （`DshDownloadViewModel.kt`，单测覆盖）。
4. **前台服务真机保活验证**：在主流厂商 ROM（小米/华为/OV/三星等）上验证
   `DshRuntimeService` 的存活与被杀恢复行为，`specialUse` 声明已就位但实际策略因厂商而异。
5. ✅ **认领进程假死**（第五轮已实现）：认领来的孤儿进程死亡后有 10s 存活巡检兜底（双条件判定），
   不再永远停在 Running。其余异常路径（装到一半切后台/断网/磁盘满等）仍需真机复现确认。
6. ✅ **停止后进程残留**（2026-10-06 已修）：真机上出现过"停止 → 下次启动报 `EADDRINUSE`"。
   根因是停止时杀的是底座进程、而 dsh 本身是它的子进程，且**发给底座的那个信号它直接忽略**
   （实际一直靠强杀收尾，而强杀来不及清理子进程）。现在三条一起上：脚本写出 dsh 的真实 pid
   供宿主精确终止、改用底座真正会响应的信号、端口仍被占时自动改用系统分配的端口。
   真机仍需确认"重试后确实能救活"。

**完成判据**
- [ ] 连续装/删/启/停 20 次以上无崩溃、无卡死、无状态残留
- [ ] 断网/切后台/转屏等异常路径均能优雅恢复
- [ ] 双实例并发安装，进度互不干扰
- [ ] 锁屏 + 后台 30 分钟后 dsh 进程仍在（至少在测试机上）

> ⚠️ **待定性（与 `design/wx-exec-proot-loader.md` §3 矛盾）**：上面第 1 条的
> `PROOT_NO_SECCOMP` 自动重试已实现，但 wx-exec 文档引用 oonid/pr 的静态分析认为
> proot 自带的 seccomp 过滤器是 dead code、该变量"设了也无意义"。
> 两边结论冲突，"重试后确实能救活"也尚未在真机证实 —— 以真机结果为准，在此之前都不要当定论。

## M4 · 可测试性与工程化（可与 M2/M3 并行）

**目标**：把"靠人工审代码才能发现"的缺陷，变成"自动化能拦住"。前四轮有几个 P0 是靠人工核对
Android 文档才发现的（比如前台服务必崩），这类应该被测试兜住。

> **现状（2026-10-30）**：单测从当时的 **148 例**涨到 **513 例 / 513 全绿**，脚本自检 28/28。
> **实际做完的是"判定核心可测化"**：修复里的判定被抽成无 Android 依赖的顶层纯函数，
> 由 `DshRuntimeRaceTest` / `R24StateMachineTest` 等钉死；R26 起再补"纯函数 + 管线断言"
> （`reconcileInstalling` 等）。**没做的是服务层本身**（`DshRuntimeService` 的
> `startForeground` 时序仍靠代码审阅，项目未引入 Robolectric）；`R24SeamTest` 只是
> **测试桩自身的冒烟**（验 `@Before/@After` 成对执行），不是服务契约测试 —— 别把它当证据。
> **CI 仍缺** —— 仓库里没有 `.github/workflows`，"编译 + 脚本 + 单测"三条线目前靠 `release.sh` 手跑。

**要做的事**
- **给 `DshRuntimeService` 加可测抽象** ❌ 未做：`startForegroundCompat` 仍直接调 `startForeground`，
  没有注入点；"任何返回前先 startForeground"这条 P0 契约目前只有代码注释与真机表现担保。
  要做就得引 Robolectric 或把服务体抽成纯逻辑类，代价不小 —— 排期前先评估。
- **给 `DshRuntime` 状态机注入"进程/时间/Context"** ◐ 半做：判定核心（状态归属、复用判据、
  pid 文件归属）已抽成纯函数并有单测；但"进程/时间/Context"本身仍未注入，
  真机时序（停到位再启、杀进程竞态）只能上真机验，单测盖不到。
- **CI 化** ❌ 未做：把三条验证（全量 `compileDebugKotlin`、脚本自检 **28 项**、JVM 单测 **513 例**）
  接进 CI；离线沙箱下 Gradle ksp 卡顿的问题仍在（`run-compile.sh` 现在用 `--offline` 绕开）。
- **修 `strings.xml` 的 aapt2 错误** ❌ 未做（**低优先**，不挡发布）：`values-de/fa/ja/pt-rBR/ru` 等
  `multiple substitutions in non-positional format`。**第五轮已证实这是"告警"不是"错误"，不会挡
  `assembleDebug`/发布**（实测 `mergeDebugResources` 打印后构建继续）。仍建议改成位置参数（`%1$s`…）
  以消警告；**切勿**用 `formatted="false"`——那会让 `getString(id, args)` 的参数不再被替换
  （界面直接显示 `%s`）。非 dsh 引入、仓库既有，建议单独立项。

**完成判据**
- [ ] `DshRuntimeService` / `DshRuntime` 关键路径有单测 —— **一半**：`DshRuntime` 侧已抽纯函数
      钉死（`DshRuntimeRaceTest` / `R24StateMachineTest` 等，513 例含 R28 的调用点契约测试）；
      `DshRuntimeService` 侧**没有**（未引 Robolectric，`startForeground` 时序仍靠代码审阅）
- [ ] CI 跑通编译 + 脚本 + 单测三条线（**没有 `.github/workflows`**，目前只有 `release.sh` 手跑）
- [x] `assembleDebug` 不再被 strings 资源错误挡住（第五轮已证实只是告警；`output/` 里已积累 fix1~fix22 共 22 个 fix 包）

## M5 · 分发与生态

**目标**：能把成品发给别人用；跟上 dsh 上游的快速迭代。

> **现状（2026-10-30）**：**发布渠道已经跑起来了** —— 签名配置（`DshReleaseKey`）、
> `dshVersion`/`dshVersionCode`/`dshFixLabel` 三段版本号规范、每版 `RELEASES.md` 发布说明、
> `output/` 里的 fixN 历史包与 `SHA256SUMS`；APK 以 **GitHub Release 附件**分发
> （`gh release list` 实测：0.1.0 起 28 个 Release，fix1~fix22 中只有 fix5 未单独发）。
> **没做的是 rootfs 分发优化与兼容矩阵** —— APK 仍是"rootfs 整包"，且没有成文的
> "dsh × Node × rootfs" 验证矩阵。另外上游追得不够：预装/验证的 dsh 版本停在
> 0.1.6-alpha.2，而上游 `latest` 已是 0.2.1-rc.5（BL-191）。

**要做的事**
- **发布渠道** ✅ 已落地：签名策略（`FCL/build.gradle.kts` 的 `signingConfigs`）、版本号规范
  （`gradle.properties` 三段式）、变更日志（`RELEASES.md` + `CHANGELOG.md`）；
  分发方式已定为**独立分发**（走 GitHub Release，不随 FCL 主线）。
- **rootfs 分发优化** ❌ 未做：rootfs 几百 MB 直接塞进 APK 太重，仍待选型
  「首启从可信源下载 rootfs」/「按 ABI 拆分 APK」/「APK 内放精简 rootfs + 首启补装」。
  相关前置在 BL-191/BL-192（rootfs 重建）。
- **跟随 dsh 上游** ◐ 半做：`version` 文件 / `scriptsVersionPair` 已有脚本版本比对机制，
  安装页能装 0.2.x；但**预装 rootfs 里的 dsh 仍是 0.1.6-alpha.2**，
  "定期验证新版本并锁版本"没有固定节奏。关注上游对原生模块 ABI、profile、鉴权方式的变更。
- **多版本兼容矩阵** ❌ 未做：尚无成文矩阵记录"哪个 dsh 版本 × 哪个 Node × 哪个 rootfs"验证过。

**完成判据**
- [x] 有可分发的签名 APK 与发布说明（**fix6 / 2026-10-19 起**：`release` 变体、正式包名、
  非 debuggable、新私钥 `release-key/dsh-release.jks`；每版 `RELEASES.md` 有发布说明）
- [ ] rootfs 分发方案落地（不再让 APK 无谓膨胀）
- [ ] 有 dsh 版本兼容矩阵并定期更新
