# 怎么写版本说明（Release Notes）

> 这份规则适用于**本项目所有产品**，不限于某一份 `RELEASES.md`。
> 写任何面向用户的版本说明前，先读完这一份。

## 一句话原则

**版本说明是写给用户的，不是写给自己的。**

用户打开 Release 页只有一个问题：**"这一版对我有什么用，我要不要装？"**
凡是不能帮助他回答这个问题的内容，都不该出现在这里。

---

## 一、判断标准：这句话该不该写

写完每句话，问自己三个问题：

| 问题 | 不通过时怎么办 |
|------|---------------|
| 用户能看懂吗？（不假设他懂代码、知道项目内部编号） | 换成日常说法 |
| 用户关心吗？（能帮他决定"要不要装、怎么用"吗） | 删掉，或移到内部文档 |
| 这是事实吗？（数字和结论都实测过吗） | 去验证，或者不写 |

---

## 二、结构：固定四层，不要自由发挥

```markdown
## 版本号（状态）

> 一句话说清这一版最要紧的变化。

### 新增 / 变更 / 修复 / 安全 / 已知边界
### 升级须知
```

### 2.1 版本标题

```markdown
## 1.4.0
## 1.4.0（fix26，当前验证包）
## 1.3.2（历史验证包）
```

括号里只放**状态**（当前 / 历史 / 已废弃），不放解释，不放技术描述。

### 2.2 一句话摘要（必须有）

紧跟标题的 `>` 引用块，**一到两句**，说清这一版__对用户__最要紧的变化。

```markdown
> **你添加的模型提供方不会再消失了。** 此前重启一次，自己配的就被抹掉，且没有任何提示。
```

**反面例子**（真实事故）：

```markdown
> **0.1.6 的第二十轮**——第三轮锐评的结果。**最要紧的一条：不要把实例的 home 目录选成工作区。**
```

问题：「第二十轮」是内部编号，用户不知道也不关心；「第三轮锐评」是内部流程，属于自说自话。

### 2.3 分类小节

用 [Keep a Changelog](https://keepachangelog.com/) 的六个分类，**按此顺序，用不上的不写**：

| 分类 | 什么时候用 |
|------|-----------|
| `### 新增` | 用户能看到的新功能 |
| `### 变更` | 已有功能的行为变了（含"更正上一版说错的话"） |
| `### 废弃` | 即将移除的东西 |
| `### 移除` | 这一版删掉的东西 |
| `### 修复` | 修掉的缺陷 |
| `### 安全` | 凭据、权限、越权相关 |

外加两个不属于 Keep a Changelog、但面向用户的版本说明需要的：

| 分类 | 什么时候用 |
|------|-----------|
| `### 已知边界` | 这一版**明确没修**的问题。写出来比藏着强 |
| `### 升级须知` | 要不要卸载、会不会重新下载、装完怎么验证 |

### 2.4 升级须知（必须有）

至少说清三件事：

- 能不能**直接覆盖安装**，还是要先卸载
- 会不会触发**重新解压 / 重新下载 / 迁移数据**，大概多久
- 装完**怎么确认装对了**（比如关于页应显示什么）

## 三、八条硬规则

### 规则 1：同一版本里，`### 修复` 只能出现一次

有多件事要修，用 `-` 列表分条：

```markdown
### 修复

- **A 问题**：……
- **B 问题**：……
```

**不要写**：

```markdown
### 修复（A 问题）
### 修复（B 问题）      ← 禁止
```

### 规则 2：标题里不放括号解释、不放技术名词

```markdown
### 修复                          ✅
### 修复（launcher.patch.yml 覆盖） ❌
### 关于测试（这次说点实话）         ❌
### 一件没解决的事（重要）           ❌
### 已知边界（这一版没解决的）        ❌
```

**标题就是分类名。** 需要解释的话放进条目正文。
括号里写"重要""请务必看""诚实说明""这次说点实话"这类，是**在跟评审者说话**，不是在跟用户说话。

### 规则 3：写"用户感受到什么"，不写"我改了哪行"

| ❌ 内部视角 | ✅ 用户视角 |
|---|---|
| 改写了 gateCopied 标记的生命周期 | 复制链接成功后不再反复弹同一个框 |
| 把 repair() 挪到 IO 线程 | 界面不再卡顿 |
| SIGQUIT 后改用 ProcessUtil.isAlive 判定 | 停止失败时不会再谎报"已停止" |

技术细节（根因分析、变异验证、单测条数）**放进内部记录**（BUGLEDGER / CHANGELOG / 提交说明），
不放进用户版本说明。

### 规则 4：不写内部编号和内部流程

```markdown
> **0.1.6 的第二十轮**——第三轮锐评的结果。       ❌
> **这一版修好了空框问题。**                       ✅
```

"第 N 轮""锐评""返工""六路并行审查""结构钉"——这些是团队内部的词，用户读不懂也不需要懂。

### 规则 5：不许前向引用

一个版本的说明里，**不能提到比它更晚的版本**：

```markdown
（写于 fix19 的说明）
> 这个数字当时不准——此后 fix21 更正过、fix22 重新测量。   ❌
```

写这段的时候 fix22 还不存在。读者看到的是时间错乱。

**正确做法**：说"本版未解决，后续版本已处理"，或干脆只描述本版的事实。
**修法**：如果后来发现某版说明有问题，就**去改那一版**，而不是在新版里解释旧版。

### 规则 6：不许写"装 xxx.apk（关于页应显示 xxx）"

Release 页本身就在分发那个 APK，文件名和版本号在页面上已经出现三次了。
这句话占地方、零信息量，还容易在复制粘贴时带上错版本号。

### 规则 7：没解决的事要写出来，但不能夸大已修的

```markdown
### 已知边界

- **A 问题：没修。** 原因是……
- **B 问题：修了第一种情况，第二种（一直转圈）没修。**
```

**不能**把"两种症状其实是两种病"写在 `### 修复` 下面，让读者以为两种都修了。

### 规则 8：数字必须实测

版本说明里的任何数字（体积、耗时、测试条数、下载量）都必须**自己量过**。

真实事故：曾写"首屏 545 KB"，实际是约 5 MB——只量了主包，漏了 58 个插件包。
被写错的数字比不写更糟，因为读者会拿它做决定。

## 四、自检清单

发布前逐条过一遍：

- [ ] 每个版本段都有**一句话摘要**，且那句话里没有内部编号
- [ ] 同一段里 `### 修复` **只出现一次**
- [ ] 所有 `###` 标题里**没有括号**
- [ ] 没有任何**前向引用**（提到更晚的版本）
- [ ] 没有"装 xxx.apk（关于页应显示…）"这类冗余句
- [ ] 没解决的事写在 `### 已知边界`，没有藏在 `### 修复` 里
- [ ] 每个数字都实测过，或者删掉
- [ ] 页面正文里没有"重要""请务必看""诚实说明""说点实话"这类旁白

自动化建议：

```bash
# 检查重复标题（同一版本段内）
awk '/^## /{delete seen} /^### /{if($0 in seen) print "DUP: "$0; seen[$0]=1}' RELEASES.md

# 检查标题里的括号
grep -n "^### .*（" RELEASES.md

# 检查前向引用（fixN 段提到 fixM 且 M>N）
awk '/^## .*fix([0-9]+)/{match($0,/fix([0-9]+)/,a); cur=a[1]}
     {line=$0; while(match(line,/fix([0-9]+)/,b)){ if(cur>0 && b[1]>cur) print NR": fix"cur" → fix"b[1]; line=substr(line,RSTART+RLENGTH)}}' RELEASES.md
```

## 五、常见误区

| 误区 | 为什么错 |
|------|---------|
| "写得越详细越好" | 用户只想知道"要不要装"。细节淹没结论，等于没写 |
| "内部编号能体现工作量" | 用户不关心你修了几轮，只关心他遇到的问题有没有解决 |
| "括号里加个说明更清楚" | 标题会变长、变乱、变得不能扫读。分类名就该是分类名 |
| "把根因分析写进版本说明显得专业" | 专业感不来自术语，来自"用户能不能自己判断"。根因放内部文档 |
| "旧版本写错了就在新版更正" | 用户看新版时会困惑"哪个版本说的对"。**回改旧版**才对 |
| "没修的部分不提，免得难看" | 用户遇到问题时找不到答案，只会更不信任 |

## 六、和内部文档的分工

| 文档 | 读者 | 写什么 |
|------|------|--------|
| `RELEASES.md`（本规则管的） | **用户** | 这版对我有什么用、要不要装、装完怎么验证 |
| CHANGELOG | 开发者 | 每次提交改了什么（可停止维护，但别假装在维护） |
| BUGLEDGER | 维护者 | 缺陷的现象、根因、修法、验证证据 |
| 提交说明 | 未来维护者 | 为什么这么改 |

**一份内容只写一处。** 版本说明里不要复制根因分析，内部文档里不要复制用户话术。
